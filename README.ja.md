# Open Rocket.Chat Client

[English](README.md) · [Tiếng Việt](README.vi.md) · **日本語**

[Rocket.Chat](https://rocket.chat) 互換サーバーで使える、コミュニティ主導の独立したフロントエンドです。React 19、Vite、Tailwind で構築され、静的ファイルとしてどこにでもデプロイできます。

このプロジェクトの目的は、ユーザーが毎日使う画面を自分たちで管理できるようにすることです。Rocket.Chat に同梱される UI とは切り離されているため、サーバーとは別のタイミングで更新できます。また、ひとつのログインセッションで複数の Rocket.Chat サーバーに同時接続できます。

> **Rocket.Chat Technologies Corp. とは無関係であり、同社による承認もサポートも受けていません。**
> これはコミュニティプロジェクトです。「Rocket.Chat」は各権利者の商標であり、ここでは互換性を説明する目的でのみ使用しています。

![ライトテーマとダークテーマのクライアント](docs/screenshot-light.png)

このクライアントは [Open Rocket.Chat Gateway](https://github.com/zscontributor/open-rocket-chat-gateway) を介して Rocket.Chat と通信します。ゲートウェイが安定した API を提供し、Rocket.Chat の認証トークンをサーバー側で安全に保管するため、ブラウザが保持するのは JavaScript から読み取れない `HttpOnly` セッションクッキーだけです。

## なぜ作ったのか

[Z-SOFT](https://z-soft.com.vn) は Rocket.Chat を実際の業務で運用しており、そこで感じた課題をきっかけに、このクライアントをオープンソースにしました。組織やコミュニティ向けに Rocket.Chat を運用している方なら、同じような悩みを抱えているかもしれません。

**Rocket.Chat 付属の UI は、長期的なカスタマイズには向いていません。** 公式フロントエンドは Rocket.Chat のモノレポ内にあり、Meteor と密接に結び付いています。ブランドに合わせる、別の製品に埋め込む、レイアウトを見直すといった変更を加えるには、コードベース全体と向き合い、アップグレードのたびに独自の修正を引き継ぐ必要があります。このリポジトリではフロントエンドだけを独立させました。初回読み込みは gzip 後で約 400 kB、絵文字データとシンタックスハイライト用の遅延チャンクを含めても約 580 kB の静的バンドルです。Meteor やサーバーランタイムは不要で、文書化された API を基盤として開発できます。

**サーバーをアップグレードしても、ユーザーの画面まで変える必要はありません。** Rocket.Chat を更新すると、通常は同梱のフロントエンドも変わり、画面の配置や見た目、操作手順まで変化します。特定の画面を前提に社員研修やマニュアル作成、ブランド調整を行っている組織にとっては、予定外の案内や再教育が必要になります。このプロジェクトでは UI を独立したリリースとして管理します。セキュリティ修正やサーバー機能を取り込むために Rocket.Chat を更新しても、ユーザーの画面は _自分たちが_ 更新すると決めるまで変わりません。[ゲートウェイ](https://github.com/zscontributor/open-rocket-chat-gateway) が Rocket.Chat の API バージョン差を吸収し、クライアントにはバージョン管理された一貫した API を提供します。

**複数のサーバーに、一度のログインで接続できます。** 一般的な Rocket.Chat フロントエンドは、ひとつのデプロイにつき 1 サーバーを前提としています。そのため、社内・顧客・コミュニティのサーバーを行き来する人は、複数のタブを開き、切り替えるたびにログインし直さなければなりません。このクライアントでは、ひとつのセッションが各サーバーへの接続を同時に維持します。再認証なしですぐに切り替えられ、開いていないサーバーの未読数やメンション数も更新され続けます。ひとつのサーバーからサインアウトしても、ほかの接続には影響しません。詳しい仕組みは [コード構成](#コード構成) を参照してください。

## アーキテクチャ

```
┌────────────────────────────────────────────────────────────────┐
│  Browser · apps/web                                            │
│  React 19 static bundle. Holds one opaque HttpOnly session     │
│  cookie — never a Rocket.Chat token.                           │
│                                                                │
│   ┌───┐  server rail     query cache            one WebSocket  │
│   │ A │◀── active        ['server', <id>, …]    for every      │
│   │ B │                                         server         │
│   └───┘                                                        │
└──────────────────────┬───────────────────────┬─────────────────┘
                       │                       │
             HTTPS /api/v1                 WSS /ws
      session cookie + X-Server-Id      session cookie
                       │                       │
                       ▼                       ▼
┌────────────────────────────────────────────────────────────────┐
│  Gateway · apps/gateway                                        │
│  NestJS + Fastify, a single Node process                       │
│                                                                │
│  session store — in memory, or Redis for more than one         │
│  instance:   cookie ──▶ { A: X-Auth-Token, B: X-Auth-Token }   │
│                                                                │
│  one upstream connection per session per server, shared by     │
│  every tab that session has open                               │
└────────┬───────────────────────┬───────────────────────┬───────┘
         │                       │                       │
   REST + DDP              REST + DDP              REST + DDP
  X-Auth-Token            X-Auth-Token            X-Auth-Token
         │                       │                       │
         ▼                       ▼                       ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Rocket.Chat A  │     │  Rocket.Chat B  │     │  Rocket.Chat …  │
│    + MongoDB    │     │    + MongoDB    │     │                 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

この構成には、次の 4 つの特徴があります。

- **Rocket.Chat のトークンはブラウザに渡りません。** ページが保持するのは JavaScript から読み取れないクッキーだけで、サーバーごとの `X-Auth-Token` との対応付けはゲートウェイが行います。画像や添付ファイルも同じ理由でプロキシされます。`<img>` タグは認証ヘッダーを付けられないためです。
- **複数サーバー、ひとつのセッション。** 同じクッキーで再度サインインすると、既存のサーバーを置き換えるのではなく _追加_ されます。レールでの切り替えはクライアント側のスコープ変更にすぎず、往復も再サインインも発生しません。ひとつのサーバーからサインアウトしても、他は接続されたままです。
- **ひとつの WebSocket ですべてのサーバーのイベントを受け取ります。** 各イベントには `serverId` が含まれ、該当するサーバーのキャッシュに反映されます。そのため、現在開いていないサーバーの未読数も更新されます。Rocket.Chat への接続はセッションとサーバーの組み合わせごとに 1 本だけ作られ、すべてのタブで共有されます。タブを 5 枚開いても接続は 5 本に増えません。
- **Rocket.Chat サーバーは、手を加えていない通常のデプロイです。** 互いのことも、この構成のことも知りません。ルーム id が 1 台のサーバー内でしか一意でないのも、ここでのあらゆるパスにサーバーが含まれるのも、そのためです。

## 現状

すでに動作しているものです。

**サインインとアカウント**

- 二要素認証を含むパスワードサインインと、サーバーが提供する OAuth プロバイダー。ボタンは `auth/servers` の応答から描画されるため、プロバイダーごとのハードコードはありません
- セッションはサーバー側で保持。アカウントメニューから 1 サーバーだけ、または全サーバーからサインアウト
- プレゼンス（オンライン・離席・取り込み中・オフライン表示）とステータスメッセージ。サーバーごとに独立して設定
- 自分の画像の変更、または削除してイニシャル表示に戻す。サーバーごとに独立して設定

**ルーム**

- チャンネル・プライベートグループ・ダイレクトメッセージをひとつのサイドバーに集約。お気に入りでまとめ、`⌘K` / `Ctrl+K` で名前による絞り込み
- チャンネル / グループの作成、ダイレクトメッセージを開く、ルームの編集・退出・非表示・お気に入り・未読にする
- ルームに画像を設定（サイドバーと情報パネルに表示）、または削除
- コンテキストバー: ルーム情報、メンバー、メンバー追加、ユーザーカード、ファイル、ピン留め / スター / メンションの一覧、スレッド、ルームごとの通知設定、prune（一括削除）、キーボードショートカット一覧
- ルーム内検索

**メッセージ**

- 無限スクロールで遡れる履歴。日付区切りと投稿者のグルーピングつき
- 送信・編集・削除。Markdown に加え、書式メニューと `⌘B` / `⌘I` / `⌘U` などのショートカット
- 絵文字リアクションと絵文字ピッカー。サーバーのカスタム絵文字も含みます
- スレッド、ピン留め、スター
- `@ユーザー`・`#チャンネル`・`/コマンド` の入力補完。スラッシュコマンドはサーバー上で実行されます
- ドラッグ＆ドロップまたは添付トレイからのファイルアップロード、画像の拡大表示、GIF 検索、ボイスメッセージ。録音内容は送信前にトレイで再生して確認できます

**通知と未読**

- 権限確認と通知音に対応したデスクトップ通知。通知するかどうかは Rocket.Chat と同じルールで判断し、ウィンドウのフォーカス、現在開いているルーム、プレゼンス、ルームごとの設定を考慮します
- 未読バッジは _すべての_ 未読メッセージを数え、メンションは色だけを決めます。Rocket.Chat と同じルールなので、未読が 12 件ある人に「1」と表示することはありません
- 未読数とメンション数は、いま見ていないサーバーでも動き続けます

**リアルタイム**

- ひとつの WebSocket 上でのメッセージ・入力中インジケーター・プレゼンス。自動再接続と、接続が劣化している間のバナー表示つき

**外観・言語・拡張**

- ライト・ダーク・システム連動のテーマ。テーマはスタイルシートではなくトークンのオブジェクトです。[docs/theming.md](docs/theming.md) と `@open-rocket-chat/theme` を参照してください
- 英語・ベトナム語・日本語に対応。[docs/i18n.md](docs/i18n.md) を参照してください
- サイドバー項目・メッセージアクション・コンポーザーアクション・設定パネルを追加できるプラグイン SDK（`@open-rocket-chat/plugin-sdk`）

**マルチサーバー**

- 複数の Rocket.Chat サーバーへの同時接続。切り替えレール、サーバーごとの未読バッジ、そして切り替え時の再ログインは不要
- ルームへのディープリンク（`/servers/:serverId/rooms/:roomId`）

未実装: 開封確認、インストール可能なオフライン対応（web manifest とアイコンは同梱していますが、Service Worker はありません）、デスクトップ版のパッケージング。
Rocket.Chat への直接接続モードについては、そもそも予定がありません。理由は後述します。

### Omnichannel は含まれていません

Rocket.Chat の **Omnichannel**（Livechat）にある、カスタマーサポート担当者向けの機能はまだ実装していません。キュー、担当者への割り当て、チャットの受け付け、部門、転送、定型文、履歴付きの終了処理、訪問者・連絡先パネルは利用できません。Web サイトに設置する訪問者向けチャットウィジェットは Rocket.Chat の別製品で、このプロジェクトの対象外です。

通常のルーム処理に付随して動くものはあります。サインイン中のアカウントがすでに参加している Omnichannel ルームはサイドバーに現れ、他のルームと同じように読み・送信・リアクションができます。Livechat のシステムメッセージ（チャット開始、終了、転送、保留、履歴送信）も、生のイベント名ではなく適切なラベルで表示されます。メンバー管理はそれらのルームでは正しく隠されます。Omnichannel ルームには管理すべきメンバー構成が存在しないためです。

これは将来も対応しないという意味ではなく、現時点で未実装ということです。Z-SOFT はこのクライアントを社内チャット向けに開発しており、Omnichannel を必要としていませんでした。不完全な管理画面を公開するより、必要な機能を段階的に追加するほうがよいと考えています。**必要な方は、ぜひ実装してプルリクエストを送ってください。** まず [ゲートウェイ](https://github.com/zscontributor/open-rocket-chat-gateway) に Livechat API を追加します。スキーマは `packages/api-contract`、データの正規化は `packages/rc-adapter`、ルートは `apps/gateway` に置きます。それらが揃ってから、こちらの UI から利用できるようになります。両リポジトリにまたがる変更の進め方は [CONTRIBUTING.md](CONTRIBUTING.md) を参照してください。たとえば最初はキューとチャットの受け付けだけを実装し、転送は後に回すなど、完成した小さな単位で送るほうがマージされやすくなります。

## クイックスタート

ゲートウェイと Rocket.Chat サーバーが必要です。後者用の Docker Compose ファイルはゲートウェイのリポジトリに同梱されています。

```bash
# 1. Rocket.Chat + MongoDB、続いてゲートウェイ（ゲートウェイのチェックアウト内で）
pnpm install && pnpm run build
pnpm run rc:up
cp apps/gateway/.env.example apps/gateway/.env
pnpm --filter @open-rocket-chat/gateway dev      # http://localhost:4000

# 2. このリポジトリ
pnpm install
pnpm --filter @open-rocket-chat/web dev          # http://localhost:5173
```

`admin` / `admin-password-123` でサインインできます。Docker Compose の起動時に作成される初期アカウントです。

ふたつのリポジトリは並行して開発されています。このリポジトリは pnpm の `link:` 設定を使い、隣に置かれた gateway リポジトリから `@open-rocket-chat/api-contract` を読み込みます。パッケージが npm に公開されるまでは、両方のリポジトリを同じ親ディレクトリに配置してください。詳しくは [CONTRIBUTING.md](CONTRIBUTING.md) を参照してください。

### GIF 検索

メッセージ入力欄からは [GIPHY](https://giphy.com/) を検索できます。API キーが必要です。
[GIPHY developer dashboard](https://developers.giphy.com/dashboard/) で無料のキーを取得し、次のいずれかを行ってください。

- `apps/web/.env` に `VITE_GIPHY_API_KEY` を設定してビルドに含める
- **Settings → GIFs** に貼り付けて、そのブラウザ内だけに保持する

API キーがなくても、GIF 検索以外の機能はすべて使えます。GIF ボタンを押すと、API キーが必要であることが表示されます。
選んだ GIF はダウンロードされ、通常の添付ファイルと同じようにルームへアップロードされるため、リンクプレビューが無効な環境でも表示されます。

## ゲートウェイが必須である理由

このクライアントは、必ずゲートウェイを経由して Rocket.Chat と通信します。ブラウザから Rocket.Chat サーバーへ直接接続するモードは、セキュリティ上の理由から意図的に用意していません。

Rocket.Chat の REST API は `X-Auth-Token` ヘッダーで認証します。ブラウザから直接接続する場合、そのトークンをブラウザ内に保存しなければなりません。トークンがあれば、すべてのルームの閲覧、本人としての投稿、プロフィールの変更など、アカウント全体を操作できます。ページや依存パッケージに XSS 脆弱性がひとつでもあれば、トークンを盗まれるおそれがあります。

ゲートウェイを経由すれば、ブラウザが持つのは自身では読むこともできない不透明なセッションクッキーだけになります。Playwright スイートは実行のたびにまさにそれを検証します。

```ts
expect(exposed.local).not.toMatch(/authToken|X-Auth-Token/i);
```

直接接続とゲートウェイ接続の両方に対応すると、この安全性をすべてのユーザーに保証できなくなります。さらに、2 種類の通信経路を維持し続ける必要があり、安全性が各環境の設定に左右されてしまいます。ゲートウェイは単一の Node プロセスで、Docker イメージと Compose ファイルも用意されています。この追加構成よりも、トークンをブラウザに置かない保証を優先しました。

クライアント自体を静的ホスティングしたい場合は、組織で 1 台のゲートウェイを共有し、すべてのクライアントからそこへ接続してください。クライアントは静的なまま運用でき、トークンもサーバー側に保持できます。

## 本番ビルド

```bash
pnpm run build
```

`apps/web/dist` は静的バンドルです。Nginx、CDN、任意の静的ホスティングで配信できます。Node.js ランタイムは不要です。

ビルド時に `VITE_GATEWAY_URL` へゲートウェイの公開オリジンを設定してください。ゲートウェイがアプリと別サイトにある場合は、さらに HTTPS 上で `SESSION_COOKIE_SAMESITE=none` を有効にし、`CORS_ORIGINS` にこのアプリのオリジンを列挙する必要があります。同一サイト構成ならどちらも不要です。

開発時は Vite が `/api` と `/ws` をゲートウェイへプロキシするため、セッションクッキーは同一オリジンに保たれ、その設定自体が不要になります。

## コード構成

```
apps/web/
├── src/features/     auth、rooms、messages、notifications、realtime — ドメインごとに 1 フォルダ
├── src/ui/           表示用プリミティブ（Radix + Tailwind）
├── src/stores/       Zustand: UI の状態とトースト
├── src/i18n/         機能ごとの JSON 名前空間を言語ごとに
└── src/lib/          SDK インスタンス、クエリクライアント、キャッシュキー、永続化
packages/client-sdk/  型付きゲートウェイ呼び出しと再接続するリアルタイムチャネル
packages/theme/       テーマの契約、同梱テーマ、その適用処理
packages/plugin-sdk/  拡張ポイントとプラグインレジストリ
e2e/                  実スタックに対する Playwright テスト
```

**状態は役割ごとに分けています。** ルーム、メッセージ、プロフィールなど、サーバーから取得するデータは TanStack Query だけで管理します。リアルタイムイベントも同じキャッシュへ反映されるため、コンポーネントは HTTP と WebSocket のどちらから届いたかを意識しません。Zustand が管理するのは、テーマ、入力中の下書き、開いているスレッド、入力中のユーザーなど、UI 側だけで必要な状態です。これにより、サーバーデータを 2 か所に持って同期する問題を防ぎます。

**ルーティング** は現在、ルーターライブラリを使わず、History API を数行呼び出すだけで実装しています。画面が 2 つだけなので、今のところ専用ライブラリは必要ありません。設定画面や管理画面が増えた段階で導入できます。パスにサーバーを含めるのは、Rocket.Chat の id がサーバー内でしか一意でないためです。複数サーバーに接続すると `/rooms/:roomId` だけではルームを特定できません。以前の形式のリンクは、現在選択中のサーバーを使って解決されます。

**マルチサーバーは、切り替え可能なデータの範囲として実装しています。** ひとつのセッションで複数の Rocket.Chat サーバーに接続でき、`<ServerScope>` が配下のコンポーネントをひとつのサーバーに関連付けます。各フックは `serverId` を引数で受け取る代わりに、そのスコープからクライアントとキャッシュキーを取得します。キャッシュキーはすべて `['server', <id>, …]` の形式なので、別のサーバーへ切り替えても元のデータはキャッシュに残ります。リアルタイム用 WebSocket はこのスコープの _外側_ に置かれ、すべてのサーバーのイベントを受信します。イベントに含まれるサーバー情報を使って正しいキャッシュへ反映するため、別のサーバーを開いている間も未読数が更新されます。

## テスト

```bash
pnpm run typecheck
pnpm run test         # ユニットテスト: テーマ契約、ロケールの整合、通知ルール、未読の計算
pnpm run test:e2e     # Playwright、起動中のスタックに対して実行
```

ユニットテストでは、ブラウザを使わずに検証できるルールを確認します。たとえば、通知を表示する条件、未読バッジの件数、各言語に英語版と同じキーが揃っているか、テーマが定義どおりか、といった項目です。

Playwright スイートはスタック全体 — アプリ、ゲートウェイ、実物の Rocket.Chat — を動かします。壊れやすいものは、部品と部品が接するところにしか存在しないからです。クッキーのフラグ、WebSocket のアップグレード、プロキシされたメディアなどがそれにあたります。検証項目にはたとえば、ページから Rocket.Chat のトークンに到達できないこと、そしてあるブラウザコンテキストで送ったメッセージがリアルタイムチャネル経由で別のコンテキストへ届くことが含まれます。
